# 04. События, данные клиента и производительность

## Три правила данных

1. **Клиент не отдаёт всё сразу.** `C_Item.GetItemInfo` → `nil` до загрузки; коллекции
   и журналы отвечают по одному объекту за вызов; сумки меняются. Любой «список на 20 000»
   — это цикл вызовов, и его нельзя делать в `OnEvent`.
2. **Кэшировать, а не спрашивать повторно.** У Drop Ledger `Stats.lua`/`ns.ItemMeta`
   держат name/качество/иконку на предмет; инвалидация — точечная, по
   `GET_ITEM_INFO_RECEIVED(id)`.
3. **Инвалидировать по событию, а не по таймеру.** `BAG_UPDATE` → сброс кэша сумок;
   `TRANSMOG_COLLECTION_UPDATED` → пересобрать индекс внешностей; `SPELLS_CHANGED` →
   переиндексировать заклинания профессий.

## Скан порциями (чтобы не подвешивать игру)

```lua
local QUEUE, STEP = {}, 250

local function ScanStep()
    local done = 0
    while #QUEUE > 0 and done < STEP do
        local id = table.remove(QUEUE)
        if not db.scan.items[id] and C_TransmogCollection.PlayerHasTransmog(id) then
            db.scan.items[id] = true
        end
        done = done + 1
    end
    ns.UI.UpdateScanProgress()
    if #QUEUE > 0 then
        C_Timer.After(0, ScanStep)      -- следующий кадр
    else
        ns.UI.OnScanDone()
    end
end
```

250 вызовов за кадр — безопасно (в Drop Ledger так сканируются десятки тысяч предметов
меньше чем за секунду суммарно, без фризов). Больше — уже заметно на слабых ПК.

Результат скана кладётся в БД (`db.scan = { items, chars, counts, byCat, ach }`) и
переживает перезаход. Автоскан — не чаще раза в час/три дня и только при входе в мир,
с переключателем в настройках.

## События добычи: что реально приходит

| Событие | Когда | Что брать |
|---|---|---|
| `LOOT_OPENED` | окно добычи открылось | `GetLootSlotLink(i)`, `GetNumLootItems()` |
| `LOOT_READY` | окно готово (12.x при автоподборе `LOOT_OPENED` может не прийти) | те же слоты |
| `CHAT_MSG_LOOT` | строка добычи в чате | текст; ссылки может не быть — искать `[название]` |
| `ENCOUNTER_LOOT_RECEIVED` | лут с босса | `itemID`, `itemLink`, `quantity`, `encounterID` |
| `MERCHANT_SHOW` | торговец открыт | ассортимент и цены доступны только сейчас |

Практика: засчитывать выпадение по **любому** из них, но гасить дубли окном 1–2 секунды
(один и тот же предмет приходит и окном, и строкой чата). Рыбалка в 12.x: `IsFishingLoot()`
плюс наличие рыбы из своей базы в окне; заброс — `UNIT_SPELLCAST_CHANNEL_START` **и**
`UNIT_SPELLCAST_START` (клиент может отдать любой).

Убийства:

* боссы — `BOSS_KILL(encounterID, name, difficultyID, groupSize)`; `encounterID` — ключ
  журнала, точное совпадение;
* дополнительно `ENCOUNTER_END` (в нём есть success) — тот же бой приходит двумя путями;
  защита от двойного счёта: запомнить `lastBossID`+время и игнорировать повтор в пределах
  10 секунд;
* редкие мобы без боевого лога — `PLAYER_TARGET_CHANGED` + `UNIT_HEALTH` (нулевое здоровье
  пока цель удерживается). Оценочно, поэтому выключателем и по умолчанию off. В подземельях
  здоровье может быть секретным — `ns.Open()` и молчание.

## Счётчики: персонаж — источник истины

Схема, которая пережила несколько патчей:

```
DropLedgerCharDB (per-character)   -- { items = { [id] = { tries, wins } } }
DropLedgerDB.chars[me][id]         -- зеркало персонажа
DropLedgerDB.acc[id]               -- сумма по всем персонажам (пересчитывается)
```

`SyncChar()` на `PLAYER_LOGIN`: счётчики персонажа копируются в `chars`, `acc`
пересчитывается по всем персонажам. Плюс счётчик `kills` — убийства источника пишутся
**всегда**, а попытки начисляются только отслеживаемым предметам; поэтому предмет,
добавленный после 40 убийств, получает 40 попыток («догон»), а база не распухает.

## Кэш с временем жизни

```lua
local bagsCache, bagsAt = nil, 0

function ns.Bags()
    local now = GetTime()
    if bagsCache and now - bagsAt < 2 then return bagsCache end
    local set = {}
    for bag = 0, NUM_BAG_SLOTS do
        for slot = 1, C_Container.GetContainerNumSlots(bag) do
            local id = C_Container.GetContainerItemID(bag, slot)
            if id then set[id] = true end
        end
    end
    bagsCache, bagsAt = set, now
    return set
end

function ns.ClearBagsCache()
    bagsCache, bagsAt = nil, 0
end
-- событие: BAG_UPDATE / BAG_UPDATE_DELAYED -> ns.ClearBagsCache()
```

Правило: кэш живёт до события, таймер — только как страховка (2 секунды), чтобы не
сканировать сумки на каждую строку списка.

## Математика дропа (частый вопрос «сколько ждать»)

Пусть `p` — шанс за попытку (доля 0..1), `n` — попытки:

```
вероятность «не выпало за n»:   (1 - p)^n
ожидание до первого дропа:      1 / p
попыток до уверенности C:       ceil(ln(1 - C) / ln(1 - p))
осталось до 90%:                max(0, попыток_до_90 - попытки_аккаунта)
```

Показывать это как ориентир, а не гарантию: шансы не накапливаются. Для `p = 0` —
прочерк, делений на ноль не должно быть.

## Живой лог событий (Trace) — лучший инструмент диагностики

Идея простая и окупается: пока вкладка «Анализ» открыта, аддон подписывается на ~60
безопасных событий и пишет строки «что пришло → что аддон с этим сделал». Закрыл вкладку —
отписался. Формат:

```
12:31:07.482  [LOOT_READY]    слотов 3, рыбалка: да
12:31:07.483  [аддон]         рыбалка: +1, зона 4395 (Даларан), попытки: 3 предметам
12:31:09.011  [UNIT_SPELLCAST_START]  спелл 7620 (Рыбная ловля) → fishing
```

Требования: имя события в каждой строке, единый счётчик времени (не `os.clock` в разных
местах), ограничение буфера (например 500 строк), кнопка «Текст лога» с **выделяемым**
текстом (`EditBox`, multi-line, `SetFocus`, `HighlightText`), фильтр «только аддон».
Не логировать в бой и не логировать секретные значения — писать «скрыто клиентом».

## Производительность: чеклист

* Нет постоянных `OnUpdate`; нет тикеров, если окно закрыто.
* Тяжёлые обновления окна — по требованию (`Refresh`), а не на каждое событие.
* Один обход сумок на серию проверок, кэш 2 с / по `BAG_UPDATE`.
* Метаданные предмета — одна запись в кэше; пришло `GET_ITEM_INFO_RECEIVED` — обновить
  одну строку.
* Индексы (по NPC, по боссу, по внешности) строятся лениво при первом обращении и
  сбрасываются событием.
* Скан — порциями; прогресс виден пользователю.
* Свой замер: `debugprofilestop()` вокруг `Refresh` + счётчик вызовов; команда
  `/ma perf watch` печатает FPS и миллисекунды аддона за 2 секунды. Так можно честно
  ответить «тормозит не аддон».

## Хранение: что в БД, а что в файлах

* `Data*.lua` — статические базы (генерируются, руками не правятся): предметы, луты,
  шансы, модели, зоны. Большие (сотни КБ), грузятся вместе с аддоном.
* SavedVariables — только пользовательское состояние: настройки, счётчики, снимки сканов,
  позиции окон. Компактно: числа/булевы/короткие строки.
* Предметы в таблицах лута хранятся строкой `"1,2,3"` и разбираются при первом обращении —
  экономия размера файла в разы (проверено на 19 000 предметов).
* Снимки сканов живут в БД, потому что нужны между сессиями; производные индексы —
  в памяти, их всегда можно пересобрать.

## Целостность данных

* `db.version` + `ApplyDefaults` (см. `01-anatomy.md`) на входе.
* Никогда не падать на мусоре из БД: `tonumber`, проверка типа, фолбэк на дефолт.
* Валидация внешних генераторов: `lua_check.py` (баланс блоков) + счётчики записей
  (`grep -c '^    \[' DataX.lua`) + тесты на нескольких реальных записях.
* Команда «сбросить X» должна быть в интерфейсе, иначе пользователь правит БД руками.
